### Engineering constraints fixed by existing requirements

1. **Credentials:** one application resolver owns source selection: authenticated CLI, then `credentials.json` in `%APPDATA%/StoryMapper` or `~/.config/storymapper`, then `GITHUB_TOKEN`. This ordered source selection is explicitly required, not an error-recovery workaround. An absent source advances to the next; malformed/unreadable selected file, invalid selected credentials and provider failures are actionable errors, not a silent switch to another account. A missing file does not fail if another permitted source is usable. CLI status/resolution must use the same actual identity even when GitHub environment variables are present; `gh` subprocess environment must not silently override the selected source. A pasted candidate is verified directly in memory; final UI shows which source the normal resolver will actually use if CLI has precedence. Provider code consumes resolved auth and does not independently read secrets. Credential-status reads are local availability probes, not authentication/provider calls; no mounted status check may call network-backed `gh auth status` while GitHub is off. Distinguish configured from explicitly verified credentials.
2. **Secret storage:** token write is an explicitly authorized human credential action outside SQLite, never an operation, Activity payload, tool argument or Project file. Use atomic replacement and POSIX 0600, safe parent/file handling and sanitized errors. Do not log request bodies, candidate tokens, subprocess output containing credentials, or verification response secrets. Tests generate a non-production canary in memory and inspect actual outputs; never use real credentials or committed secret fixtures. Token-file failure must leave the switch off; if later SQLite confirmation fails after a successful file write, report that retained file effect and the unchanged connection/switch. Do not claim cross-file/DB atomicity. No automatic login is launched by this preparation.
3. **Canonical identity:** keep AD-10's scoped uniqueness and one `github` binding per entity. Canonical external ids are normalized GitHub HTTPS Issue/Milestone locators (canonical owner/repository casing, positive number, no query/fragment); the adapter alone creates/changes them after validated input. A connection is configuration, not identity: two connection ids targeting the same Issue cannot duplicate/reassign its local binding. `remote_work_item_links` owns `external_ref_id`, connection association and synchronization baselines/state, not repeated `cardId`/`releaseId`/remote locator/URL identity. Public projections join canonical refs. Generic external-ref writes continue to refuse `github`; adapter-produced operations need validated scope and evidence, not a caller-controlled source string as authority.
4. **Provenance and lifecycle:** re-key `card_github_evidence` to canonical references; source-only evidence is distinct from outbound sync ownership. Copy retains provenance and source pointers, without making two Cards in one scope own the same Issue or granting a copy outbound ownership. Deleting an owner/reference explicitly updates every affected surviving evidence owner with versions/history/audit, including logically removed Maps. Archived/parked is not deleted. Before hard deletion removes live references, record a typed `externalRef.deleted` Activity event for the GitHub ref, with deletion reason `entity-deleted`, Project/Map/entity identity and the canonical before snapshot, in the same transaction. 7.3 supplies that contract and indexed/scoped repository read; 7.6 consumes non-undone events without a current equivalent live binding for `local_deleted` health. Source detach, park/archive and ref rebind are not entity deletion. Reuse Activity persistence instead of a new tombstone table; historical payloads cannot resolve a live binding. Never recreate deleted local Cards or remote Issues automatically.
5. **Schema boundary:** follow AD-9: pre-release development databases are disposable; no migration/backfill of old prototype GitHub tables or compatibility reader is promised. Update bootstrap in `connection.ts` and Drizzle declarations together, then populated current-schema reopen/Restore/integrity tests. 8.1 owns the first release migration baseline. A changed operation shape increments the existing operation schema version, makes old pending proposals stale through the existing transition, and preserves historical payloads as history. No automatic conversion or execution of old `githubLink` commands.
6. **Exports:** moving GitHub refs to `external_refs` must not export the Sync aggregate inadvertently. Keep non-GitHub refs/source-plan baselines; redact GitHub refs, adapter sync/evidence/outcomes and their Activity/ChangeSet/copied-map payloads from portable Project archives. Extend import validation to refuse unredacted GitHub rows. Operational restore points retain sync data but never credentials. CSV/Markdown/board/filter/risk projections all read the same joined identity. Do not delete all external refs to obtain redaction.
7. **Remote plan:** 7.4 owns one persisted Dry Run contract, distinct from SQLite ChangeSets. Store plan id, exact Issue/Milestone items, scope, initiating actor and captured versions/content/connection/mapping fingerprint plus database epoch. Confirm is human-only and references that plan id; `confirm:true` plus a new selection is insufficient. Empty explicit selection never expands to the whole Map. Selection changes, Restore, connection/mapping changes, conflicting or changed local/remote inputs require a new preview. Refresh remote inputs at confirmation; GitHub lacks a general atomic multi-Issue transaction, so retain truthful per-effect results and do not promise rollback or isolation from concurrent external editors.
8. **Remote effect lifecycle:** persist each Issue/Milestone intent before its first modifying provider call. Use an opaque stable marker in the machine footer (not mutable title/map name/prefix) for interrupted-create reconciliation, while human footer text names Story Map and Card Key and links to the Card deep route using the current served loopback origin and Project/Map/Card ids. Marker lookup must be complete for the exact repository/scope and may not treat an incomplete search/transport error as absence. On ambiguous outcomes stop visibly; do not blindly retry a create. Record successful identity/outcome before moving to the next effect. Resume is explicit, keeps the original marker/payload and first reconciles in-flight items. Restore does not undo remote effects; a re-push of the same local entity uses its stable marker even when local intent rows were rewound. Shared Milestones are listed once with dependencies; compound provider calls must not hide unreviewed Milestone creation, type changes, state changes or label writes.
9. **Actor boundary:** every incoming domain change, including human-triggered import/pull/remote conflict resolution, is a ChangeSet proposed by actor `github`, retaining the initiating human/Agent identity. Preserve protection, approval, restore-point, root-version and atomic audit rules from ADR 0003/0004. Agent push under protection is `protected` before provider/credential writes; otherwise it may only propose a Dry Run. Generic ChangeSet approval, including `allowAgentApproval`, never authorizes remote writes. All outbound paths (quick push, sync, local conflict choice, Card modal, toolbar) use the same human confirmation; no alternate direct-write endpoint.
10. **Merge representation:** use one canonical title/description/footer and label normalization for plan, three-way merge, persisted baseline, conflict diff and health. Strip only the well-delimited machine footer, preserve authored Markdown, and do not write generated footer back into local description. Never serialize local Workflow Status into the Issue body. Preserve unrelated labels and hierarchy override semantics. For opted-in Annotations, the effective local Annotation name is the label mapping: only labels matching unambiguous existing scoped definitions are managed, assignments synchronize, and unknown remote labels stay unrelated. Do not auto-create an Annotation for every remote label or delete reusable definitions when removing an assignment. Initial Unscheduled placement retains separate acknowledged local/last-observed remote baseline values, so a first explicit Release sync can propose assignment instead of interpreting initial null as remote Milestone removal. Release ↔ Milestone identity is canonical, not a mutable title match. Map Release name, goal to Milestone description, releaseDate to due date and released/open state through previewed items; startDate has no Milestone counterpart and stays local. Clearing a value is an explicit effect. Iteration remains the existing inbound-only option; do not add ProjectV2 writes.
11. **Conflicts and provider errors:** extend/reuse `conflictResponseSchema`/conflict entries as the single ConflictReport wire contract; do not add a parallel envelope merely because the story capitalizes that name. One unresolved conflict per canonical ref/field; repeated refresh does not erase the reviewed local/remote evidence. Convergence does not silently close an existing conflict. Only touched fields are blocked and the server enforces this, including generic ChangeSet/upsert/HTTP paths. Local-wins remote effects await Dry Run confirmation before resolving the conflict; cancel/failure retains it. Remote-wins local changes use the executor. Read-only prevents local-wins remote application until made writable. Treat absent/not-accessible distinctly from transport/auth/rate-limit/partial GraphQL failures; a masked GitHub 404 is not proof of deletion. Last known identity remains navigable with truthful stale/error information.
12. **Ticket creation:** accept canonical `https://github.com/owner/repo/issues/N`, `owner/repo#N`, and positive `N`/`#N` only with an explicit selected/default connection. Reject PR URLs, foreign hosts/schemes, embedded credentials and repository mismatches before a provider call. A duplicate existing binding focuses/reports the existing Card, never creates a second one. Use the composer-selected level/parent/position/Release rather than silently replacing its location from the remote hierarchy. Notes cannot acquire outbound Issue ownership. Revalidate lookup/scope/database epoch before atomic Card + canonical ref + source evidence apply. Connection-dialog detours and failed lookups retain the draft.
13. **Provider seam:** retain `WorkItemProvider` in its actual existing package and `PublishProvider` in core, unless a later specific requirement justifies moving them. Add normalized provider methods only for required type discovery, explicit Milestone effects and reconciliation. Application orchestration consumes normalized values; no `provider === github` conflict-resolution branch in shared flows. 7.8 adds a test-only provider module plus the contracts enum/registry/credential registration changes; GitHub implementation/tests remain byte-identical for that extension exercise. No production second provider, publish implementation, plugin loader, OAuth backend or background polling.
14. **Mounted state:** all new dialogs/panels obey existing scope/epoch admission, pending-write holds, response adoption, deep links, explicit Reload/Keep mine and focus restoration. A late verification/plan/import result cannot enable a different Project, resurrect a pre-Restore plan or overwrite a dirty composer. Use central English strings and current Dialog/board state infrastructure.

## Verification strategy

1. Contracts/core: strict source/plan/item/conflict shapes; deterministic identity/footer/status/label normalization; exact selected-set and dependency effects; unknown provider refusal; no remote or DB I/O in core.
2. DB: real disposable SQLite, populated current-schema reopen/Restore, explicit root version/history changes, unique scoped refs, copies/source evidence, deletion history, operation schema transition and archive export/import redaction with non-GitHub refs retained.
3. Server: actual human HTTP plus both MCP transports using fake providers; no outbound writes without the exact confirmed plan; no provider traffic while off except the specifically agreed D1 boundary; protection/permission flips and Restore at every provider await; incoming domain/audit failures roll back together.
4. Recovery: twelve Issue items, terminate after item six and separately after a provider success before local persistence; reopen and resume with exact per-item accounting, one remote item per marker, persisted Milestone effects, no blind create after uncertain/partial lookup. Repeat after local Restore and with concurrent local/remote edits.
5. Web: connected connection → bulk Dry Run → partial retry → import → field conflict → resolution → health → single-ticket composer; retain hidden selection counts and Notes exclusion. Exercise dirty draft, inactive scope, pending operation, lower-version Restore and late responses across all new dialogs.
6. Native acceptance: keyboard-only dialog/field diff/confirmation, focus return, zoom/contrast, real browser links and screen-reader matrix. Use disposable provider fixtures for deterministic acceptance. A real GitHub smoke is separately authorized, presence-confirmed if login is required, and never inferred from this preparation.
7. At implementation completion run focused suites, workspace tests, capability parity, typecheck/build and `node scripts/verify.mjs` under Node 24. Preserve exact failures; do not relax gates or infer acceptance from sprint rows.
